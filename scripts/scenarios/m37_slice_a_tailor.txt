# M3.7 SLICE A -- sheep -> wool -> spinning wheel -> yarn -> loom -> bolt ->
#                  scissors -> cloth -> a tailored item.
#
# RUN AS SESSION 11 (RevolutionWeaver), created the ordinary way with
#   --create-skills 34:50,44:30,11:20    Tailoring 50 / Lumberjack 30 / Carpentry 20
#   --create-stats  50:20:10             STR 50 / DEX 20 / INT 10
# Source-X clamps each skill to 50 and the sum to 100, each stat to 60 and the
# sum to 80, and picks the kit itself. Nothing is GM-provisioned.
#
# WHY STR 50 HERE TOO. A bolt of cloth is WEIGHT=50.0, and NEWBIE TAILORING
# hands out one free -- so a STR-30 tailor is already half-loaded before it
# weaves. The first run's loom DID produce a bolt and the shard answered
# "You put the bolt of cloth at your feet. It is too heavy." The chain worked;
# the character could not hold the result.
#
# WHY THE KIT MATTERS, item by item:
#
#   NEWBIE TAILORING      -> i_sewing_kit  (t_sewing_kit: the tool the cloth
#                            menu opens from) and ONE i_cloth_bolt, which is
#                            STARTING STOCK and is deliberately not used --
#                            mark_item baselines it so the proof is a delta.
#   NEWBIE LUMBERJACKING  -> i_hatchet (0x0F43), TYPE=t_weapon_axe, which is an
#                            IT_WEAPON_AXE and therefore a legal shearing blade
#                            (CClientTarg.cpp:1866-1890).
#   MALE_DEFAULT          -> a dagger and starting gold.
#
# WHY THIS PROOF WAS IMPOSSIBLE BEFORE M3.7, twice over:
#
#   1. There was no spinning wheel and no loom anywhere in the world. Zero, on
#      the whole shard.
#   2. Even a MAP STATIC wheel would not have worked. CClient::Event_Target
#      resolves the target with uid.ObjFind() (CClientEvent.cpp:2481); a static
#      has no UID, so pItemTarg is nullptr and the IT_WOOL / IT_YARN cases in
#      OnTarg_Use_Item break out having done nothing. The station MUST be a
#      dynamic item, which is exactly what the shard's own world decorator
#      places -- and which had never been run.
#
# THE STATIONS, from Scripts-X's own city_britain_deco_felucca.scp:
#   spinning wheel  (1473,1689,0)
#   upright loom    (1473,1685,0) + (1474,1685,0)
# Both ground level, inside the Britain tailor shop the atlas calls
# britain_tailor_2 (1467,1686,0). No coordinate here was invented.
#
# THE ENGINE NUMBERS BEING TESTED:
#   shear         1 pile of wool, sheep -> CREID_SHEEP_SHORN, regrows in
#                 WoolGrowthTime = 30 minutes (sphere.ini:399)
#   wool -> yarn  1 pile yields THREE balls, and there is NO skill check at all
#                 (CClientTarg.cpp:2066)
#   yarn -> bolt  FOUR units accumulate in m_itLoom, then one bolt drops
#                 (CClientTarg.cpp:2230)
#   bolt -> cloth the bolt's own RESOURCES: FIFTY cloth (CItem.cpp:4287)
#
# ON THE SCISSORS. Bolt-to-cloth is IT_SCISSORS only -- a dagger will not do it
# (CClientTarg.cpp:2147). Scissors are in no newbie kit, and this character's
# Tinkering 30 cannot craft them without tinker tools it also lacks. They are
# therefore BOUGHT from the Britain tailor for a few gold of the character's own
# starting money. That is a TOOL purchase, not a resource purchase: it shortcuts
# no chain -- the wool must still be sheared, spun and woven -- and it is
# recorded explicitly rather than glossed over. See the vendor matrix's open
# question on tool grading.
#
# Nothing here spawns wool, yarn, a bolt, cloth or a finished garment.

# EVERY REPEAT PASS MUST RE-OPEN THE PACK FIRST, and must `require`.
#
# The resolver answers from the client's container snapshot, and only an 0x3C
# refills it. Without the re-open, `remember yarn3` handed back the uid of the
# yarn pass 2 had already CONSUMED; `use` on a dead item draws no target cursor
# and `wait_target` then blocks forever. That is exactly how the previous run
# died -- two bolts finished, then silence at line 285 until the harness
# timeout. It never reached a single assertion.
#
# `require` is the second half of the fix: it turns "no yarn left" into a named
# abort instead of a hang. A pass that cannot run should say so.

# -------------------------------------------------------- 7. tailor an item
# The cloth menu opens by using the SEWING KIT on cloth (sm_tailor_cloth).
# i_sash is Tailoring 4.5 and costs 4 cloth + 1 thread -- and note the thread:
# a wool-only tailor can weave cloth and cannot sew it, because Tailoring
# recipes consume THREAD (from cotton), never yarn. If the sash is refused for
# want of thread that is a real finding, not a scenario bug.
# THE TARGET IS A BANDANA, AND IT IS EXPECTED TO FAIL.
#
# i_bandana (0x153F) is Tailoring 0.1 -- the cheapest garment on the shard --
# and it costs `RESOURCES=2 i_cloth,1 i_thread`. This character has cloth it
# wove itself and no thread at all, so the shard should refuse it. That refusal
# is the finding: 264 recipes in runtime/scripts spend i_cloth, and every one
# that a tailoring menu can reach also spends i_thread.
#
# WHERE THREAD ACTUALLY COMES FROM is engine-decided, not script-decided.
# CClientTarg.cpp:2053 handles IT_WOOL and IT_COTTON on a spinning wheel:
# "1 pile of wool yields three balls of yarn" (this run measured exactly 0 -> 3)
# and "1 pile of cotton yields six spools of thread". i_thread's own script line
# `RESOURCES=1 i_flax_bundle` is a value declaration for <resmake>, NOT a
# production path -- the engine never reads it to make thread.
#
# So a wool tailor cannot sew. Cloth and thread come from DIFFERENT crops, and
# a self-sufficient tailor needs sheep AND a cotton field.
mark_item 0x153F

remember cloth pack_graphic 0x175D
require cloth
use @kit
wait_target
target @cloth
sleep 2500

# NO BANDANA. Asserting "unchanged" rather than "gained" is the whole point:

# somewhere this scenario did not account for, and that is worth the abort.
