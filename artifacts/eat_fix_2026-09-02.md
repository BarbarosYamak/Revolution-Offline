# Eat loop defect — root cause and fix (2026-09-02)

Defect as reported: 7 characters at the Britain provisioner loop
`[life] food: eating` -> `action_result: use_object timeout` every ~4 s,
~200x each; GET_FOOD abandons at 300 s and re-picks.

## Two independent causes, both verified

### 1. `use_object` on food can never confirm (the timeout stream)

Verified source behaviour — `CChar::Use_Eat`,
`server/Source-X/src/game/chars/CCharUse.cpp:929-993`: a double-click on food
answers with a **system message and nothing else**. Either a refusal
(`food_cantmove` / `food_canteat` / `food_rcanteat` / `food_canteatf`) or,
after `Use_EatQty`, exactly one of six `food_full_N` lines selected by
`index = IMulDiv(Stat_GetVal(STAT_FOOD), 5, uiFoodMax)` (:967-991).
No container gump, no target cursor, no menu.
`CItem::ConsumeAmount` on a stack of 2 only decrements it, so there is no
`0x1D` delete either.

`Client::ActionUseObject` (src/Client.cpp:3106) accepts as confirmation only
0x24 container, 0x6C cursor, 0x7C menu, or a *recognised* 0x1C line
(`ActionOnSysMessage`, src/Client.cpp:4027). None of the eat vocabulary was
recognised, and `ActionOnObjectDeleted` (:4203) does not handle
`Kind::UseObject`. So every eat sat pending for the full `kUseTimeoutMs`.

Verified runtime evidence — `run_gates/g_Halain.console.txt` (wave 09:09):

```
139 [09:09:25.563] food: eating (hungry=1 starving=0, carrying 2)
141 [09:09:25.563] [ACTION] use_object serial=0x40010BE3
143 [09:09:25.563] Halain: *You eat some bread loaves*
144 [09:09:25.563] System: You eat the food, and begin to feel more satiated.
146 [09:09:29.571] event action_result: use_object timeout
147 [09:09:29.633] food: eating (hungry=1 starving=0, carrying 1)
150 [09:09:29.647] System: You are nearly stuffed, but manage to eat the food.
158 [09:09:33.661] event action_result: use_object timeout
```

Note the FIRST eat also timed out — the report's "only the first eat succeeds"
is not what the log shows; the server ate the food every time and the client
recognised none of it. 351 `food: eating` lines in that one session.

### 2. Hunger was a login snapshot that eating never cleared (the loop)

`Runner::Observe` read hunger as *"was `you are hungry` said at any point since
session start"* (old src/life/Runner.cpp:1487-1490). The shard says it rarely:
`CChar::OnTickFood` (`server/Source-X/src/game/chars/CCharAct.cpp:5789-5806`)
emits `MSG_HUNGER` + the `looks %s` emote only on a food-decay tick and only
while `Food_GetLevelPercent() <= 40`. `runtime/sphere.ini:694 Regen3=1800`, so
that tick is once per 30 minutes.

`g_Halain.console.txt:39` is the **only** hunger line in the whole session:
`[09:09:02.898] System: You are hungry`. It then latched `hungry=1` forever, so
Halain ate his pack out, walked to the provisioner, bought more, ate that, and
repeated — the 200x loop. World save at the end: `FOOD=14 MAXFOOD=15` (93% —
stuffed) while the client still believed he was hungry.

## Fix

Both server statements are about the same `STAT_FOOD`, on two scales:
status line = `food*8/max` (8 bands, `CCharStatus.cpp:837,870-885`),
eat line = `food*5/max` (6 bands). `act::HungerStatements()` maps both onto the
8-band scale, each eat phrase to the hungriest band it can mean (never claims a
character is fuller than it is). `Runner::Observe` now takes the **newest**
statement by timestamp, so eating clears hunger and the next 30-minute decay
tick re-asserts it.

- `include/uo/actions.h` — `act::EatOutcome` + `ClassifyEatMessage`,
  `act::HungerStatement` table + `kHungerLevelHungry/Starving`.
- `src/Client.cpp` (`ActionOnSysMessage`) — eat text finishes a `UseObject` /
  `UseItemOn`: `Ate` -> Success, `AlreadyFull` -> InvalidState (nothing was
  eaten and nothing should be retried), `CannotEat` -> ServerFailure.
- `src/Client.h`, `src/travel/ClientTravel.cpp` — `JournalLastSaidMs`, the
  "when was it last said" read that "newest statement wins" needs.
- `src/life/Runner.cpp` (`Observe`) — newest-hunger-statement-wins.
- `tests/m2_actions.cpp` — `TestEatClassification`: the six `food_full_N`
  lines, the two refusals, the whole statement table on the hungry/starving
  boundary, and the login-line-then-meal ordering regression.

No hard-coded success: every outcome comes from a line the server actually
sent, quoted from Source-X / `runtime/scripts/core/messages.scp:167-175,470-477`.

## Long-run result — the eat itself, live

`Regen3=1800` (runtime/sphere.ini:694) means the food-decay tick that emits the
hunger warning fires once per 30 minutes, so proving the eat needed a gate
longer than that. 35-min gate, Draver (`FOOD=4/15`, carrying bread) —
`run_gates/g_Draver.console.txt:92-108`:

```
 92 [10:08:51.929] System: You are hungry
100 [10:08:51.930] food: eating (hungry=1 starving=0, carrying 2)
104 [10:08:51.945] System: You eat the food, and begin to feel more satiated.
105 [10:08:51.945] [ACTION_RESULT] use_object success (15ms) You eat the food, ...
108 [10:08:54.455] food: fed, and carrying 1 for later -- this errand is done
```

One eat, confirmed in 15 ms where it used to time out at 4000 ms, hunger
cleared by the meal, goal finished, next goal taken. Whole 35-min session:
1 `food: eating`, 0 `use_object timeout`. The two hunger ticks in Dorvar's
session are 10:09:43 and 10:39:45 — 30 minutes apart, exactly `Regen3`.

## Second defect found in the same run: a fisher starving with dinner in its pack

`run_gates/g_Dorvar.console.txt:584` "You are starving" (FOOD=0/15) while
carrying `i_fish_cut_cooked`, and the GET_FOOD errand stood down as "carrying
the catch -- cutting and cooking it rather than buying bread" thirteen times
(lines 276, 1313, 2367, 3455, 4509, 5681, 6989, 8169, 9276, 10479...) without
ever eating. Cause: `kFood` (src/life/Runner.cpp:105) did not contain 0x097B
`i_fish_cut_cooked`, which is `TYPE=t_food` on this shard
(runtime/scripts/items/i_profession_cook_barkeep_baker.scp:113-115), so the eat
branch found nothing and fell through to the fisher stand-down. Added.

Verified live afterwards, 40-min gate, Dorvar (`FOOD=0/15`) —
`run_gates/g_Dorvar.console.txt:8394-8425`:

```
8394 [11:09:47.582] System: You are starving
8417 [11:09:51.434] food: eating (hungry=1 starving=1, carrying 1)

8422 [11:09:51.449] [ACTION_RESULT] use_object success (15ms) After eating ...
```

He ate the steak he was carrying, the server confirmed it in 15 ms, and the

stands down to cook more. Session totals: 1 eat, 0 `use_object timeout`,
1 stand-down — against 0 eats and 13 stand-downs in the same character's
pre-fix run.

## Known limitation (not fixed, not in scope)

The client only learns its hunger from the server's own statements, and
`OnTickFood` makes one every 30 minutes (`Regen3=1800`) and only below 40%.
So a bot can be hungry for up to half an hour before it knows. That is the
shard's cadence, not a client bug; anything faster would need the bot to ask
(there is no client-visible "what is my hunger" request other than the same
tick message), or a `Regen3` change, which is a shard tuning decision.
