## Cluster-by-cluster

**1. Door-adjacent move REJECTED (21/30 chars).** Root cause found: NOT a
defect. Traced Draver (Navigation.cpp OnMoveReject/BotDoorRetryWasTried)
end-to-end: first reject at 18:08:59.956 -> OpenDoor+retry -> one more
reject on the same edge -> blacklist+reroute -> arrived normally 17s
later, then continued navigating (bank, tinker, mobile) for the rest of
the run. Spot-checked Aelia (many further "arrived at" lines through
18:12:50) and Rhea (her only door event is followed by nothing at all --
her run is silent because no goal was ever selected, a life/planner gap,
not navigation). This cluster is first in every log only because login
always drops a character at a threshold; it is not the cause of standing
still. Not fixed because nothing was broken.

**2. "goal (X,Y) is not walkable" spam (Dorvar x60, Halain x34, Titus
x12).** Root cause found, two layers:
- `src/life/Runner.cpp:5508` and the old `:9637` stored a resource's own
  unwalkable tile (a tree trunk / open-water cast target) as the "proven"
  resource location, then a later trip fed that literal tile straight to
  `TravelToPoint`. Fixed the fishing half (Runner.cpp:9632-9642): the
  memory write now uses `obs.x/obs.y` (the character's own stand tile,
  stationary while fishing) instead of `fishX_/fishY_` (the water tile),
  matching the already-correct dock-arrival write at Runner.cpp:9718.
- Systemic gap: `ActionGoto`/`BotStartGoto` never carried an arrival
  radius down to A*, so ANY caller handing Navigation a literal
  resource tile (the chop-stand case included, `chopX_/chopY_` at
  Runner.cpp:5257/5508 is the tree's own tile) got an instant, repeatable
  "goal not walkable" abort. Fixed at the root in
  `src/navigation/Navigation.cpp` (`BotPollPathPlanner`): one snap to the
  nearest walkable tile via the new `nav::FindWalkableNearGoal` ring
  search (`include/uo/nav_rules.h`) is tried before giving up, bounded to
  once per trip (`BotState::goalSnapTried`, `kGoalSnapMaxRadius=6`).

**3. Amara boxed in, A* "no path", start open=0 terrain=8.** Root cause
found via `path_probe.exe 1124 362 5 1124 372 10`: her own standing tile
is NOT walkable (`walkable=0`), and the entire 21x31 tile window around
her is uniform deep-water land (z=-5, zero statics anywhere -- no boat
deck, no dock). This is a stale/invalid persisted login position (very
likely captured while she was on a boat that is no longer there), not a
navgrid or A* defect: Navigation already fails in one clean, correctly
diagnosed `BotAbortPath("no path")` per attempt (no retry loop at this
layer), and the life layer already gives up appropriately after 3 trips
("three trips did not arrive"). The real defect -- why she then sits idle
for the rest of the run instead of trying anything else -- is a
persistence/session-state issue (what wrote her last position, and boats
not being modelled in the static navgrid at all) outside
navigation/travel ownership, and outside the "no state.json edits" /
"don't touch Needs/Identity/Professions/Goals.cpp" boundaries for this
pass. Reported, not fixed; recommend a follow-up task for whichever
agent owns session persistence / boat-multi tracking.

**4. "13 lookahead repairs without movement; abandoning trip" (8
chars).** Root cause found: `BotState::lookaheadPatches` was a per-trip
cumulative counter (only reset in `BotStartGoto`/`BotFollowTick`), so a
long, crowded route (Britain-area traffic) that was genuinely still
advancing racked up >12 patches over many real steps and self-aborted
anyway -- contradicting its own log message ("without movement"). Traced
Vorar (path length 46->43->31->24->19->18->16->10->9 over 18s, i.e. real
progress) and Falen (11 patches in 5s while still walking, "arrived...
stopped short by 3" immediately after) hitting the cap while still
working. Fixed: `nav_.bot.lookaheadPatches` now resets to 0 whenever a
step is actually sent (`Navigation.cpp` `BotPumpMoves`, `StepSubmit::Sent`
branch), so the counter now measures what its own message claims:
consecutive repairs with zero intervening progress.

**9. Moongate (3564,2140) friction (Ithion 10x no-path).** Root cause
found via `path_probe.exe 3560 2136 22 3564 2140 20 34`: a plain flood
fill (no A* heuristic, no grass/foliage penalty) reaches the gate fine
(1745 cells reachable in the window) -- the route genuinely exists.
Traced the live failure to `src/travel/ClientTravel.cpp` `TravelDriveLeg`:
`Journey::CommandTarget` already returns the correct per-leg z
(`RouteLeg::target.z`, populated with the real atlas z for a
Moongate/Teleporter leg at `RoutePlanner.cpp:427`), but `TravelDriveLeg`
discarded it and only ever applied a z hint when the CURRENT leg's target
was within 2 tiles of the journey's ULTIMATE goal -- which a multi-leg
"walk to a gate, then transit to a distant city" journey never satisfies
for the gate-approach leg itself. The z-blind `ActionGoto(tx,ty)` then let
A* burn its whole (XY-distance-scaled) node budget probing the wrong
floor before ever finding the ramp up to the z=34 pad. Fixed: when the
current leg is a Moongate or Teleporter leg, `TravelDriveLeg` now passes
the leg's own `tz` through to `ActionGoto`.
